DEPLOYMENT · VULTR · OBSERVABILITY

signoz-vultr

Desired state for one SigNoz observability server: ClickHouse, ClickHouse Keeper, a Postgres metastore, the SigNoz application and the signoz-otel-collector ingester on a single guarded Vultr instance in Amsterdam.

One host, both halves: signoz.bigconfig.online serves the dashboard and accepts OTLP/HTTP on /v1/logs, /v1/traces and /v1/metrics over the same port 443. An exporter needs the hostname and a bearer token, and 4317/4318 are never exposed — community-edition SigNoz has no ingestion keys of its own.

What is tracked here

colors.yml (the only editable desired state), the installed signoz Package Skill payload and lockfile, a root launcher copied from that payload, toolchain files, and documentation. Credentials live in gitignored .envrc.private; generated output in .colors/ is never committed.

Lifecycle

direnv allow
./green build
./green create --dry-run
./green create

Build and dry-run are credential-free and never read ~/.ssh. Real creation converges the instance, its firewall, the proxied Cloudflare record, and the Compose stack, then proves the schema exists, the histogramQuantile function is registered, and ingestion works — by sending one OTLP log through the public path, token and all, and reading the row back out of ClickHouse. Deletion stays guarded by compute-prevent-destroy: true.

The machine keypair is not in this repository

This deployment runs in keygen mode: colors.yml carries no vultr-ssh-keys, so the package generates and owns ~/.ssh/signoz-vultr outside the checkout. Cloning this repository elsewhere does not carry machine access — copy the keypair deliberately, or create refuses rather than regenerating a key that cannot reach the live host.

Reaching the host

Convergence writes one ~/.ssh/config block following the workspace SSH Config Standard, so ssh signoz-vultr connects with no address, user or -i flag. The block sits at the top of the file, above any Host * stanza that would otherwise win on User and IdentityFile, and delete removes it before destroying the instance.

Credentials

Two secrets are generated on the server and supplied nowhere: the OTLP ingestion bearer token and the Postgres password. They land only in /etc/signoz/ingestion.env and /etc/signoz/postgres.env, mode 0600, each written once so a re-converge never rotates it. The token is what keeps the public OTLP path from being an open write into ClickHouse — SigNoz community edition has no ingestion keys, so convergence refuses to proceed if that file is ever empty, because an empty token would match a bare Authorization: Bearer.

The root account's password is the exception: it comes from COLORS_PAR_SIGNOZ_ROOT_PASSWORD, reaches the host as an Ansible lookup resolved at run time, and is that account's only record — SigNoz forbids editing or deleting the root user from the UI.
